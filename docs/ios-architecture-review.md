# iOS architecture review

The recommended architecture for PDF Algo Pro as a multi-year native Apple product, reviewed area
by area. Every major decision states its recommendation, rationale, the alternatives considered,
trade-offs, risks, the impact on future scale, and the product pillars it serves. Decisions that
must stay stable are recorded as ADRs in [adr/](adr/README.md); this review explains them together.

Owner: Architecture · Reviewed: each milestone, and whenever an ADR changes

## SwiftUI architecture

**Recommendation**
- SwiftUI for every screen. UIKit appears only inside small `UIViewRepresentable` /
  `UIViewControllerRepresentable` adapters where a framework requires it (the PDF SDK's page view,
  the VisionKit document camera, PencilKit), and only in the package that owns that capability.
- Swift 6 language mode with strict concurrency set to `complete`; warnings are errors in CI.
- The project is generated by XcodeGen from `project.yml`; the `.xcodeproj` is never committed.
- Code lives in local Swift packages, one per capability: `Core` (domain types, no framework
  imports), `PDFEngine` (the only module that imports the PDF SDK), `DocumentStore`, `Scanning`,
  `OCR`, `Intelligence`, `Search`, `Commerce`, `Telemetry`, `DesignSystem`, and `Features/*`
  (one package per feature: Library, Reader, Editor, Scan, Sign, Organize, Assistant, Settings,
  Paywall, Onboarding). The app target only composes them.
- Allowed imports follow the dependency graph below and are enforced by the `invariants` gate.

```
App ──► Features/* ──► DesignSystem
          │   └──────► Core
          ├──► DocumentStore ──► Core
          ├──► PDFEngine ──────► Core        (vendor SDK imported here only)
          ├──► Scanning, OCR ──► Core
          ├──► Intelligence ───► Core, Search (network allowed)
          ├──► Search ─────────► Core
          ├──► Commerce ───────► Core        (network allowed)
          └──► Telemetry ──────► Core        (network allowed)
```

**Rationale.** SwiftUI is where Apple ships new platform capability first. WWDC26 added a document
architecture with direct disk access, lazy prefetching containers and resizable iPhone apps
([What's new in SwiftUI, WWDC26](https://developer.apple.com/videos/play/wwdc2026/269/)). One
package per capability keeps build times, test scope and ownership clear, and matches the
local-package approach already proven in the organisation's shipping iOS app. Swift 6 strict
concurrency removes a class of data races at compile time
([Swift 6 migration guide](https://www.swift.org/migration/documentation/migrationguide/)).

**Alternatives considered**

| Option | Why not |
|---|---|
| UIKit-first | Slower to build premium adaptive UI; diverges from where Apple invests; more code to port to Mac and visionOS |
| The Composable Architecture (TCA) | Third-party framework at the core of the app; steep learning curve; the Observation framework now covers what we need |
| VIPER / Clean-architecture layers per screen | Ceremony without a matching benefit for a SwiftUI app of this size |
| One app target without packages | Fast to start, but compile times, test isolation and ownership degrade as the product grows |
| Tuist instead of XcodeGen | Capable, but XcodeGen is already the organisation's pinned, checksum-verified tool |

**Trade-offs.** Packages add a little setup and require discipline about public APIs. Strict
concurrency makes some SDK integrations (non-`Sendable` vendor types) need wrappers.

**Risks.** The vendor PDF SDK may not be Swift 6 clean: contain it inside `PDFEngine` behind
`Sendable` value types. SwiftUI gaps for heavy document UI: keep the SDK's own page view in an
adapter rather than re-implementing rendering.

**Future scalability impact.** Packages map one-to-one onto the future team map (see GitHub
governance). New platforms reuse every package except the adapters.

**Pillars served.** PIL-7 Native Apple Experience; supports all others.

## Navigation strategy

**Recommendation**
- A `NavigationSplitView` shell (sidebar: library sections and tags; content: document list;
  detail: the document). On iPhone it collapses to a stack automatically.
- Each column is driven by a typed `Route` enum held in a `NavigationPath`, stored with
  `@SceneStorage` so state is restored after the app is terminated.
- One deep-link router maps URLs (`pdfalgopro://`), App Intents, Spotlight results, widgets,
  controls and Handoff activities onto `Route` values. Nothing navigates by itself.
- Documents open in their own scene with `WindowGroup(for: DocumentID.self)`, which gives iPad and
  Mac multiple windows with no extra work. Sheets and full-screen covers are driven by one
  `Presentation` enum per scene.
- Layouts react to size classes and window size, never to device type: iOS 27 lets iPhone apps
  resize ([What's new in SwiftUI, WWDC26](https://developer.apple.com/videos/play/wwdc2026/269/)).

**Rationale.** A single router makes every entry point testable and consistent, which matters
because PDF Algo Pro is entered from many system surfaces (see the Apple-first baseline below).
Split-view navigation is the platform convention for library-style apps such as Files and Notes.

**Alternatives considered.** A coordinator object per flow (UIKit-era pattern; duplicates what
`NavigationStack` now does). Tab-based navigation (the organisation's other apps use tabs, but a
document library with sections fits a sidebar better and scales to iPad and Mac).

**Trade-offs.** Typed routes must stay `Codable` for restoration; adding a screen means extending
the enum and the router tests.

**Risks.** Deep links from untrusted sources (a shared URL) must never trigger actions without
user confirmation: the router only navigates; actions need explicit user intent.

**Future scalability impact.** The same routes serve iPad multi-window, Mac menu commands and
visionOS windows.

**Pillars served.** PIL-7; PIL-1 Document Reading.

## Dependency injection strategy

**Recommendation**
- Services are protocols in `Core` (for example `DocumentStoring`, `TextRecognizing`,
  `IntelligenceRouting`, `EntitlementProviding`). Live implementations sit in their packages.
- One `AppContainer` composes the live services at launch and is placed in the SwiftUI environment
  with `@Entry` keys. Feature models receive exactly the services they need through their
  initialisers.
- Previews and tests use a preview container with in-memory or fake services. No global
  singletons (the few Apple singletons, such as `UserDefaults.standard`, are wrapped).

**Rationale.** SwiftUI's environment already is a dependency-injection mechanism; initialiser
injection keeps models testable without a framework. This mirrors the organisation's existing
`AppContainer` pattern in its shipping iOS app.

**Alternatives considered.** Third-party DI containers (for example `swift-dependencies`,
`Factory`): capable, but a dependency at the core of the app for a problem the platform solves.
Service locators: hide dependencies and make tests order-dependent.

**Trade-offs.** Some boilerplate when a feature needs many services; mitigated by small,
focused service protocols.

**Risks.** The container growing into a god object: keep it composition-only, with no logic.

**Future scalability impact.** Per-platform containers (Mac, visionOS) swap only the adapters.

**Pillars served.** Supports all pillars through testability.

## State management strategy

**Recommendation**
- Feature models are `@Observable` final classes isolated to `@MainActor`, one per screen or
  flow, owned by the view with `@State`.
- Long-running and shared work lives in actors (document I/O, OCR queue, indexing, AI sessions)
  that return `Sendable` values. Cancellation follows structured concurrency.
- Editing uses the scene's `UndoManager`; every mutating document operation registers an undo.
- Large data never sits in observable state: page images come from the PDF engine's own tiled
  rendering or an `NSCache`-backed thumbnail cache on disk.
- Persistent user preferences use a typed settings store over `UserDefaults` (declared in the
  privacy manifest).

**Rationale.** Observation tracks only the properties a view reads, which keeps large document
screens efficient ([Observation](https://developer.apple.com/documentation/observation)). Actors
make concurrency correctness a compile-time property under Swift 6.

**Alternatives considered.** `ObservableObject` with `@Published` (older, coarser invalidation).
A single app-wide store (Redux-style): central, but every change is global and fine-grained
performance suffers on large documents.

**Trade-offs.** State is distributed across models; cross-feature coordination goes through
services and the router rather than a global store.

**Risks.** Accidental main-thread work in models: signposts and performance tests guard the
budgets in [performance budgets](performance-budgets.md).

**Future scalability impact.** Models are platform-neutral and reused unchanged on iPad, Mac and
visionOS.

**Pillars served.** PIL-1, PIL-2 Document Editing, PIL-7.

## SwiftData vs Core Data

**Recommendation.** SwiftData, behind a `LibraryStore` protocol, for the library index only:
document metadata, folders and tags, recents, favourites, OCR and search derived data, and cached
AI results. Use a versioned schema with a migration plan, and the fallback ladder already proven
in the organisation's shipping app (open on disk → recreate after a second failure → in-memory →
run without the index). The index is always rebuildable from the files.

**Rationale.** SwiftData is Apple's current persistence framework and integrates with Observation
and SwiftUI. iOS 27 adds sectioned fetches, `ResultsObserver` for observing results outside views,
and `HistoryObserver` for persistent-history changes (reported in coverage of WWDC26:
[Fatbobman's Swift Weekly #139](https://fatbobman.com/en/weekly/issue-139/);
[SwiftData documentation](https://developer.apple.com/documentation/swiftdata)). Because files are
the source of truth, a failed store never loses a user's document.

**Alternatives considered**

| Option | Assessment |
|---|---|
| Core Data | Mature, with batch operations and CloudKit sharing; more code, and no advantage for an index that can be rebuilt |
| GRDB / raw SQLite with FTS5 | Excellent full-text search; a third-party dependency (GRDB) or hand-written SQL; kept as the fallback for search if Core Spotlight is not enough |
| Files only (JSON sidecars) | Simple, but querying tags and recents across thousands of documents gets slow |

**Trade-offs.** SwiftData's CloudKit sync has constraints (no unique constraints, optional or
defaulted attributes); the schema is designed for them from day one.

**Risks.** SwiftData migration or performance issues at large library sizes. Mitigations: the
`LibraryStore` protocol (a Core Data implementation can replace it without touching features),
performance tests with a 10,000-document library, and the fallback ladder.

**Future scalability impact.** The index format can change freely because it is derived.

**Pillars served.** PIL-1, PIL-6 Offline Capability.

## CloudKit strategy

**Recommendation**
- Documents sync through the app's iCloud Drive ubiquity container (visible in the Files app as a
  "PDF Algo Pro" folder), not through CloudKit records.
- Library metadata (tags, favourites, reading position) syncs through the CloudKit **private**
  database via SwiftData's CloudKit integration.
- A small CloudKit **public** database record set carries remote configuration: feature flags and
  the AI-provider kill switch (read-only for the app).
- When iCloud is unavailable or signed out, the app works fully in local-only mode and says so.

**Rationale.** iCloud Drive is built for large files, handles conflicts with file versions and is
what users expect from a documents app; CloudKit assets are a poor fit for multi-megabyte PDFs.
Private database sync needs no server of ours and keeps data in the user's own iCloud account
([CloudKit](https://developer.apple.com/documentation/cloudkit)).

**Alternatives considered.** Our own sync backend (cost, liability and a privacy story we do not
want). CloudKit shared databases for collaboration (out of scope; see [non-goals](non-goals.md)).

**Trade-offs.** Two sync channels (files and metadata) must agree on document identity.

**Risks.** Identity drift when a file is renamed or moved on another device. This is the
**document-identity spike**, a readiness blocker (see [readiness review](readiness-review.md)):
evaluate a stable identifier stored in the file's extended attributes against the file-provider
resource identifier and content hashing.

**Future scalability impact.** Collaboration can later use CloudKit sharing for metadata without
changing where files live.

**Pillars served.** PIL-5 Privacy, PIL-6, PIL-7.

## File management strategy

**Recommendation**
- Files are the source of truth. Reads and writes are coordinated (`NSFileCoordinator`,
  file presenters) and atomic; conflicts use `NSFileVersion`
  ([NSFileCoordinator](https://developer.apple.com/documentation/foundation/nsfilecoordinator)).
- Adopt the iOS 27 SwiftUI document protocols (`ReadableDocument` / `WritableDocument`) with
  snapshot-based saving for the editor, and keep the library UI app-managed
  ([InfoQ summary of WWDC26 SwiftUI](https://www.infoq.com/news/2026/07/swiftui-wwdc26/)).
- Open in place from Files and other apps using security-scoped bookmarks; import copies into the
  library only when the user asks.
- A "Recently Deleted" area keeps deleted documents for 30 days, like Files and Notes.
- Never load a whole PDF into memory: the engine streams and renders tiles.
- Data protection: documents use `completeUntilFirstUserAuthentication`, so background indexing
  works; an optional app lock uses Face ID or Touch ID (LocalAuthentication).

**Rationale.** Users expect their PDFs to be real files they can see in Files, share, and back up.

**Alternatives considered.** An opaque app database of documents (breaks Files integration and user
trust). `DocumentGroup` only (free document browser, but no room for a library with tags, smart
folders and AI search).

**Trade-offs.** Coordinated file access is more complex than a database.

**Risks.** Corruption during a save interrupted by termination: atomic writes, and the save-integrity
test in the golden corpus suite ([testing strategy](testing-strategy.md)).

**Future scalability impact.** Works unchanged on iPad and Mac, where Finder and Files integration
matter even more.

**Pillars served.** PIL-1, PIL-2, PIL-5, PIL-6, PIL-7.

## PDF processing strategy

**Recommendation**
- A commercial PDF SDK is the primary engine from day one, behind our own `PDFEngine` protocols
  (render, text selection, annotations, forms, content editing, page organisation, redaction,
  signatures, export). Only `PDFEngine` imports the SDK. ADR-0007 stays **Proposed** until the
  vendor spike completes.
- Vendor selection by a scored matrix: true editing of existing text; on-device PDF → Word, Excel
  and PowerPoint; true redaction; digital and ink signatures; forms; iPhone, iPad, Mac and
  visionOS support; SwiftUI integration; binary size; privacy manifest and **no telemetry**;
  offline licence validation; licence cost and terms; lock-in and exit plan. Candidates:
  [Nutrient (formerly PSPDFKit)](https://www.nutrient.io/sdk/ios/) and
  [Apryse](https://docs.apryse.com/ios/guides).
- PDFKit stays for lightweight jobs that do not need the SDK (thumbnails through Quick Look,
  Spotlight text extraction) and as a contingency implementation of the read-only protocols.
- **Redaction removes content.** Covering text with a box is not redaction; the redaction path
  deletes the underlying text, images and metadata and is covered by tests that search the output
  for the removed strings.

**Rationale.** Editing existing text is the most requested task in the category (it is the first
option in competitors' onboarding) and PDFKit cannot do it. Building a content-stream editor is
years of work. Wrapping the SDK keeps the product free to switch vendors.

**Alternatives considered**

| Option | Assessment |
|---|---|
| PDFKit only | Native and free; no true text editing, no Office export, limited redaction |
| Open-source engines (PDFium, MuPDF) | PDFium is BSD-licensed but a large C++ integration without an editing layer; MuPDF is AGPL unless a commercial licence is bought |
| Build our own editor | Not a responsible use of years of engineering |
| Native text editing for the safe subset | Proposed in [ADR-0025](adr/0025-native-text-editing-for-the-safe-subset.md): erase and redraw one page's text with Core Graphics and Core Text, proving each edit; narrower than an SDK, with no third-party code |

**Trade-offs.** Licence cost, binary size and a dependency at the heart of the product, accepted
for true editing and conversion from launch.

**Risks.** Vendor telemetry or licence phoning home (audited in the spike; must be off). Price
changes (contract terms, exit plan). SDK not Swift 6 clean (contained in `PDFEngine`).

**Future scalability impact.** Mac and visionOS support depend on the vendor's platform coverage;
this is a selection criterion.

**Pillars served.** PIL-1, PIL-2, PIL-3.

## OCR strategy

**Recommendation**
- Scanning uses the VisionKit document camera (edge detection, perspective correction, multi-page)
  ([VNDocumentCameraViewController](https://developer.apple.com/documentation/visionkit/vndocumentcameraviewcontroller)).
- Recognition uses Vision's `RecognizeDocumentsRequest`, which returns document structure
  (paragraphs, tables, lists) rather than loose lines
  ([RecognizeDocumentsRequest](https://developer.apple.com/documentation/vision/recognizedocumentsrequest)).
  All OCR runs on the device.
- Recognised text is written back as an invisible text layer so scanned PDFs become searchable
  and selectable, and is indexed for search and AI.
- English and French first, then the languages Vision supports that the market needs.
- OCR runs in a bounded queue (an actor), respects thermal state and Low Power Mode, and can
  continue in the background (see background processing).

**Rationale.** On-device recognition is private, free per page, and works offline; Apple's
document-structure API avoids building layout analysis ourselves.

**Alternatives considered.** Cloud OCR services (cost, privacy, offline loss). Third-party
on-device engines such as Tesseract (larger, weaker on layout).

**Trade-offs.** Recognition quality and language coverage follow Apple's releases.

**Risks.** Accuracy on poor scans and handwriting; measured with the OCR accuracy suite (character
and word error rates per language) described in [testing strategy](testing-strategy.md).

**Future scalability impact.** The same pipeline runs on Mac with Continuity Camera as the input.

**Pillars served.** PIL-3 OCR & Scanning, PIL-5, PIL-6.

## AI integration strategy

**Recommendation**
- One `IntelligenceRouter` in the `Intelligence` package drives Apple's Foundation Models
  framework (`LanguageModelSession`, with `DynamicProfile` for switching models). Tiers:
  1. **On-device** `SystemLanguageModel`: default for everything that fits; works offline with no
     usage limit; accepts page images. Its context is **4,096 tokens per session** (instructions,
     prompt, tools, schema and output together), read at run time from `contextSize`
     ([Managing the context window](https://developer.apple.com/documentation/foundationmodels/managing-the-context-window)),
     so long documents go through chunking and on-device retrieval (`SpotlightSearchTool` scoped
     with `.focused(.documents)`). It needs an Apple Intelligence-capable device with Apple
     Intelligence turned on; `SystemLanguageModel.availability` reports why it is unavailable
     ([UnavailableReason](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel/availability-swift.enum/unavailablereason)),
     and the app then offers the non-AI features; from V2 it also offers Pro users the opt-in Claude
     tier ([PRD](prd.md), FR-ONB-006).
  2. **Private Cloud Compute** `PrivateCloudComputeLanguageModel`: 32K-token context and reasoning
     levels; requires a network connection and the `com.apple.developer.private-cloud-compute`
     entitlement; per-user daily limits tied to the user's iCloud account (`quotaUsage`,
     `quotaLimitReached`). There is no cloud cost only while the developer is in the App Store
     Small Business Program **and** under 2 million first-time downloads **and** holds the
     entitlement; past the threshold, a migration is due within 6 months
     ([Private Cloud Compute for developers](https://developer.apple.com/private-cloud-compute/),
     [Adding server-side intelligence with Private Cloud Compute](https://developer.apple.com/documentation/foundationmodels/adding-server-side-intelligence-with-private-cloud-compute)).
  3. **Claude** through Anthropic's `ClaudeForFoundationModels` package (`ClaudeLanguageModel`,
     same session API): for the longest documents and hardest reasoning
     ([Claude for Apple Foundation Models](https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/apple-foundation-models)).
- Every cloud tier is **opt-in**, with consent that names the provider and the data sent and can
  be revoked in Settings, as App Review Guideline 5.1.2(i) requires
  ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing)).
- Claude authentication: App Attest during beta (no key in the binary; Anthropic issues short-lived
  tokens to genuine installs). **Before general availability, a proxied relay
  (`pdf-algo-pro-backend`) is required**, because App Attest tokens carry no user identity and so
  cannot enforce per-user entitlements or quotas (same source).
- Answers are grounded: responses about a document cite page numbers, and the UI shows them.
- Documents are untrusted input. Prompts separate instructions from document content; the model
  may not trigger actions; tool calls are limited to read-only document tools.
- Structured extraction uses `@Generable` types (guided generation) so results are typed.
- Prompts are versioned artefacts with evaluation gates ([prompt management](prompt-management.md),
  [AI evaluation framework](ai-evaluation-framework.md)); routing and failover follow
  [model selection](model-selection.md) and [AI governance](ai-governance.md).
- App Intents expose "Summarise PDF", "Ask about this PDF" and "Extract data" to Siri, Shortcuts
  and Spotlight.

**Rationale.** A single Apple session API across all tiers keeps the code small and lets routing
change without touching features. On-device first is the privacy and offline promise the product
is built on.

**Alternatives considered.** Calling provider APIs directly from the app with an embedded key
(extractable; rejected). Our own inference servers (cost and liability). Cloud-first AI (breaks
the privacy and offline pillars).

**Trade-offs.** The on-device model is small; long documents need chunking and retrieval, and some
tasks need a cloud tier.

**Risks.** Hallucinated or uncited answers (evaluation suite, mandatory citations); prompt
injection from documents (separation, no actions, red-team set); cost overrun on the Claude tier
(token budgets, `tokenCount` pre-checks, relay quotas, spend caps); the Claude package is in beta
(wrapped behind the router, pinned version).

**Future scalability impact.** New providers plug in as `LanguageModel` conformances; the router
and evaluation suite stay the same.

**Pillars served.** PIL-4 AI Document Intelligence, PIL-5, PIL-6.

## Background processing

**Recommendation**
- `BGContinuedProcessingTask` for work the user starts and expects to finish (exporting a large
  document, OCR of a long scan), with the system's progress UI
  ([BGContinuedProcessingTask](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask)).
- `BGProcessingTask` requiring external power for library-wide work: indexing, OCR of imported
  documents, thumbnail generation.
- Short saves use a background task assertion so an edit is never lost on backgrounding.
- All queues respect `ProcessInfo.thermalState` and Low Power Mode, and cancel cooperatively.

**Rationale.** These are the system's sanctioned mechanisms; they give the best battery behaviour
and App Review compliance.

**Alternatives considered.** Keeping the app alive with audio or location background modes (a
misuse that App Review rejects and that drains battery).

**Trade-offs.** Timing of maintenance work is up to the system.

**Risks.** Large first-run indexing: progress is visible and resumable.

**Future scalability impact.** The same task identifiers work on iPad; the Mac uses the same code
with fewer limits.

**Pillars served.** PIL-3, PIL-6, PIL-7.

## Performance considerations

**Recommendation.** Performance is a requirement with budgets, measured in CI and in the field:
cold launch, first page of a large PDF, scrolling at the display's refresh rate, memory ceilings,
battery per hour of reading and per 100 OCR pages, OCR speed, and AI latency per tier. The budgets,
reference devices and measurement methods are in [performance budgets](performance-budgets.md).
Tools: `OSSignposter` intervals, XCTest performance metrics, and MetricKit reports from real
devices ([MetricKit](https://developer.apple.com/documentation/metrickit)).

**Rationale.** Apple recommends that apps render their first frame within 400 milliseconds of
launch ([Reducing your app's launch time](https://developer.apple.com/documentation/xcode/reducing-your-app-s-launch-time));
document apps are judged by how quickly large files open and scroll.

**Alternatives considered.** Ad-hoc profiling before release (regressions land unnoticed).

**Trade-offs.** Performance tests take CI time; they run on release pull requests and nightly.

**Risks.** Simulator numbers do not match devices: budgets are checked on reference devices before
each App Store release.

**Future scalability impact.** Budgets per platform are added as each platform ships.

**Pillars served.** PIL-1, PIL-7.

## Accessibility

**Recommendation**
- Dynamic Type everywhere, including the accessibility sizes; layouts reflow rather than truncate.
- VoiceOver: every control labelled; a custom rotor for PDF headings and pages; PDF content read
  from the text layer (and from OCR for scanned files), so untagged PDFs are still readable.
- Reduce Motion through one `Motion` helper; Increase Contrast colour variants; 44-point targets;
  Voice Control names; full keyboard navigation on iPad and Mac.
- "Listen to this PDF" with `AVSpeechSynthesizer`.
- Automated audits with `performAccessibilityAudit()` in UI tests
  ([XCUIApplication performAccessibilityAudit](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/performaccessibilityaudit(for:_:))),
  plus a scripted manual VoiceOver pass before each release.
- Accessibility Nutrition Labels on the App Store product page, declared honestly.

**Rationale.** Accessibility is part of the Apple quality bar and of the Human Interface
Guidelines ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)).

**Alternatives considered.** Retrofitting after launch (always more expensive and rarely complete).

**Trade-offs.** More design and test time per feature.

**Risks.** Third-party SDK views with weak VoiceOver support: an evaluation criterion in the SDK
spike, with our own accessibility layer where needed.

**Future scalability impact.** The same semantics carry to Mac and visionOS.

**Pillars served.** PIL-1, PIL-7.

## App Store compliance

**Recommendation**
- Privacy manifest (`PrivacyInfo.xcprivacy`) declaring every required-reason API, checked by the
  `invariants` gate ([Privacy manifest files](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files)).
- The privacy label describes the whole app, so it stays "Data Not Collected" only while nothing
  reaches us: V1 and V1.1 qualify; the V2 relay and opt-in telemetry change it
  ([privacy architecture](privacy-architecture.md)); any telemetry is minimal, aggregated, disclosed,
  and consented where required ([analytics strategy](analytics-strategy.md)).
- Subscriptions through StoreKit 2 (`SubscriptionStoreView`) with clear price, period, trial terms,
  restore and manage links (Guidelines 3.1.1 and 3.1.2).
- Third-party AI: consent screen naming the provider and data (Guideline 5.1.2(i)).
- No account required, so no account-deletion obligation (Guideline 5.1.1(v)) unless accounts are
  introduced later.
- Encryption export: standard encryption only; declared in the app's Info.plist.
- "Analyse Contract" carries a clear "not legal advice" disclosure.
- Full checklist: [App Store strategy](app-store-strategy.md) and
  [compliance roadmap](compliance-roadmap.md).

**Rationale.** Compliance designed in from the start avoids rejections and rework.

**Alternatives considered.** Reacting to App Review feedback (slow and risky near launch).

**Trade-offs.** Some growth tactics (hard paywalls before value, tracking-based attribution) are
ruled out.

**Risks.** Guideline changes: reviewed each milestone.

**Future scalability impact.** The same compliance baseline applies to the Mac App Store.

**Pillars served.** PIL-5, PIL-7.

## Future iPad support

**Recommendation.** Design and build for iPad from the first line of code (split view, size
classes, `Transferable`, multi-window scenes), and ship the iPad-first experience in V2: three
columns, Stage Manager and multiple windows, Apple Pencil (PencilKit, hover, squeeze on Pencil
Pro), keyboard shortcuts and the iPadOS menu bar, drag and drop between apps.
Details: [platform strategy](platform-strategy.md).

**Rationale.** iPad is where long-form reading and annotation happen; adaptive design from day one
avoids a costly retrofit.

**Alternatives considered.** A scaled iPhone app on iPad (poor experience; App Review and users
notice).

**Trade-offs.** More layout states to test from the MVP onwards.

**Risks.** Scope creep in the MVP: iPad-specific features are scheduled, only adaptivity is required.

**Future scalability impact.** The iPad layout is most of the Mac layout.

**Pillars served.** PIL-1, PIL-2, PIL-7.

## Future macOS support

**Recommendation.** A native multiplatform SwiftUI target that shares every package; Mac-specific
adapters for the PDF view, menu bar commands, Finder integration and Continuity Camera scanning.
Not Mac Catalyst.

**Rationale.** A native target gives real Mac conventions (menus, windows, keyboard, pointer)
that Mac users expect from a premium document app. Foundation Models is available on macOS 27.

**Alternatives considered.** Mac Catalyst (faster, but looks and behaves like an iPad app).
"Designed for iPad" on Apple silicon (no Mac conventions at all).

**Trade-offs.** Some per-platform adapter code.

**Risks.** PDF SDK Mac coverage (a vendor selection criterion); VisionKit's document camera is
iOS-only, so Mac scanning uses Continuity Camera.

**Future scalability impact.** Opens the Mac App Store and a desktop audience with the same
codebase.

**Pillars served.** PIL-1, PIL-2, PIL-7.

## Future visionOS support

**Recommendation.** First make the iPad app available on Apple Vision Pro as a compatible app;
later add a native visionOS target with windows and ornaments for reading and review. visionOS
must never shape V1 decisions.

**Rationale.** Demand is unproven; the compatible app costs almost nothing, and the native target
reuses the packages when evidence supports it.

**Alternatives considered.** A native spatial experience at launch (cost without evidence).

**Trade-offs.** The compatible app is not a native experience.

**Risks.** Framework availability differs (for example PencilKit and the document camera);
checked per package in the platform matrix.

**Future scalability impact.** Low cost to keep the option open because UIKit stays in adapters.

**Pillars served.** PIL-7.
